# ADR-0006: 오프라인 평가 하네스 — 프롬프트 개선 루프는 순수 Bun으로, ML 최적화 프레임워크는 미도입

## Context

프롬프트(`prompt.js`)를 고칠 때 "좋아졌는지"를 판단할 객관적 기준이 없었다. 윤문 품질의 최종 재판관은 사람이지만, 반복 가능한 보조 지표는 이미 갖춰져 있다 — 규칙 엔진이 LLM 결과를 재검증해 S1 잔존·변경률·등급을 내는 구조(웹 UI 배지와 동일)다. LLM 결과에 S1이 남는 하드케이스를 모으면 DSPy/AdalFlow류 bootstrap few-shot의 원료가 되기도 한다.

AdalFlow 같은 Python 자동 최적화 프레임워크 도입을 검토했으나, (1) 스택 충돌 — 이 프로젝트는 의존성 0개·Bun 전용(ADR-0002)이고 프레임워크는 Python 런타임을 요구하며, (2) 문제 형상 불일치 — textual gradient는 다단계 파이프라인 그래프에 힘을 발휘하는데 이 프로젝트의 LLM 모드는 모놀리식 시스템 프롬프트 하나라 최적화할 그래프가 없고, (3) 프로세스 충돌 — 룰북·프롬프트는 업스트림 벤치마킹과 references.json 큐레이션을 거치는 사람의 산물이라 자동 생성 프롬프트와 출처 추적 체계가 어긋난다.

## Decision

- **평가 하네스를 순수 Bun 스크립트로 만든다**: `lib/eval-core.mjs`(순수 로직) + `scripts/eval.mjs`(CLI) + `eval/corpus.json`(기대 신호를 태깅한 원문 픽스처). 메트릭은 규칙 엔진(`analyze`/`polish`/`changeRate`/`grade`)을 그대로 재사용한다.
- **LLM 호출은 공급자를 직접 두드리지 않는다** — 실행 중인 `serve.ts`의 `/llm/chat/completions` 프록시를 경유한다. 키 주입과 프로토콜 변환은 서버 몫이며, 스크립트는 `.env`를 읽지 않는다.
- **프롬프트 A/B는 런 파일 비교로 한다**: `--out`으로 런 JSON(모델·시스템 프롬프트 sha256·결과물 원문 포함)을 저장하고, `--prompt <파일>`로 변안 시스템 프롬프트를 넣어 `--compare`로 차이를 본다.
- **few-shot은 자동 주입하지 않는다**: `scripts/bootstrap-fewshot.mjs`가 하드케이스를 A(few-shot 후보: 엔진이 고칠 수 있는 S1 잔존 → 검증된 원문→결과 예시 쌍) / B(역주입 회귀 보고) / C(감지 전용 잔존 → 룰북 갭 과제)로 분류해 마크다운 후보를 낼 뿐, 반영은 기존 큐레이션 절차를 거친다.
- **ML 최적화 프레임워크는 도입하지 않는다.** 프롬프트 최적화 필요성이 실제로 커지고 파이프라인이 다단계로 진화하면 그때 ADR로 재결정한다. 그 전에 JS 생태계 선택지를 먼저 검토한다.

## Consequences

- **프록시 메트릭 한계를 감수한다.** 규칙 엔진은 자기가 아는 47개 패턴만 본다. "엔진 점수는 좋은데 실제 윤문은 나쁜" 프롬프트 변형(Goodhart)을 하네스가 잡지 못하므로, 런 JSON의 결과물 원문을 사람이 읽는 단계가 루프에서 빠지지 않아야 한다. 이 한계는 README와 스크립트 출력에 명시했다.
- 프롬프트 개선 제안이 "느낌"에서 "재현 가능한 런 파일"로 바뀐다. PR에 런 JSON 비교를 붙이면 리뷰어가 숫자로 검증할 수 있다.
- 코퍼스(`eval/corpus.json`)의 `expect` 태그가 규칙 임계값 변화를 감시한다 — `bun test.mjs`가 픽스처 부패·엔진 회귀를 함께 잡는다.
- 대가: few-shot 예시 쌍이 엔진 polish 결과라 LLM보다 보수적이다(문맥 수술 없음). 그럼에도 후보로 쓰는 이유는 결정적·검증 가능한 치환이라는 신뢰성 때문이며, 사람이 다듬어 반영한다.
