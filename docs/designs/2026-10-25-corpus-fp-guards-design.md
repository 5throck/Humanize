# 실문서 코퍼스 오탐 가드 설계 (보호 스팬·문맥 제외)

| Field | Value |
|-------|-------|
| Date | 2026-10-25 |
| Status | accepted (PR #17 병합) |
| Related | ADR-0001 (출처 레지스트리 — 이 가드는 자체 실측이므로 src 미표기), 2026-10-25-eval-harness-design (회귀 감시 체계) |
| 파일 | `engine/rules.js` (마스킹·가드), `test.mjs` (코퍼스 오탐 회귀 테스트) |

## Problem

65편 실제 위키 문서 코퍼스를 규칙 엔진으로 돌려 2,175건의 findings를 수집한 결과, **오탐이 특정 계열에만 몰렸다** — 규칙 로직의 문제가 아니라 "사람이 쓴 기술 문서의 정당한 용법"이 패턴과 우연히 겹치는 사각지대였다. 실문서에서 걸린 계열:

1. 백틱 인라인 코드의 검증된 UI 라벨(`버튼이 눌린 상태로 보인다` 류 문맥이 코드·설명 혼합 구역에서 발화)
2. 따옴표로 감싼 화면 카피(시스템이 보여 주는 문자열 그대로의 인용)
3. 위치 명사 뒤 "~에 있어"(`S12 줄에 있어 찾기 어렵다` — 번역투 조사가 아니라 문자적 존재 서술)
4. 표 행의 문구(STRIDE식 위협 표의 "더 이상 지원되지 않는다" — 지원 종료 기록, 수사적 재정의가 아님 / 행마다 영어 병기 — B-1이 반복 병기로 오인)

## Change Design

### D1 — 보호 스팬 마스킹 (detect/fix 공통 전처리)

detect·fix **둘 다** 실행되기 전에 백틱 인라인 코드와 이중 따옴표 스팬을 마스킹하고, 끝난 뒤 복원한다. 규칙은 보호 스팬을 보지도 고치지도 않는다 — "윤문이 화면 카피를 고쳐 버리는" 사고를 구조적으로 차단한다. 마스킹은 rules.js 내부 구현이므로 API·MCP·웹이 자동으로 같은 동작을 한다(ADR-0004 단일 엔진).

### D2 — 규칙별 문맥 가드

- **A-3 위치 명사 가드**: 토큰이 위치 명사(줄·칸·셀 등, `LOC_NOUN_RE`)로 끝나면 "~에 있어"을 세지도 고치지도 않는다. 있어요/있어 제외는 유지.
- **G-1 상태로 가드**: "버튼이 눌린 **상태로** 보인다"처럼 상태 지속 서술인 경우 추측 종결 카운트에서 제외.
- **B-1·A-24 표 행 제외**: `isTableRow`(마크다운 표 구분선·파이프 검출) 행은 통째로 스캔·수정 대상에서 뺀다 — 표는 행마다 병기·기록하는 것이 장르 관습이다.
- **C-11 fix 문맥 가드**: 쉼표 제거가 의미 구분·호흡에 필요한 자리(주어 전환 등)를 건드리지 않도록 fix 측 조건 강화.

### D3 — 양방향 회귀 테스트

`test.mjs`에 코퍼스 오탐 회귀 테스트를 넣었다: (1) 실문장 오탐 0 — 위 FP 계열 문장들이 해당 규칙을 발화하지 않는가, (2) 진짜 신호 재현 — 같은 패턴의 실제 AI 티 문장은 여전히 잡히는가. 가드가 오탐을 줄이다 정탐까지 죽이는 사고를 양방향으로 잡는다.

## Alternatives Considered

| 대안 | 기각 사유 |
|------|----------|
| 규칙별 allowlist 단어 목록 확장 | 마스킹·구조 제외가 근본 해결 — 단어 목록은 코퍼스가 늘 때마다 계속 보수해야 하고 누수가 있다 |
| 오탐 계열 규칙의 제거 | 정탐이 함께 사라진다 — 실제 AI 티에서도 같은 패턴이 나온다(양방향 테스트가 검증) |
| 문맥 판단을 LLM에 위임 | 규칙 엔진은 결정적·오프라인이 존재 이유(ADR-0002). 문맥 가드는 정규식으로 표현 가능한 좁은 조건에 한정해 유지 |

## Verification

- `bun test.mjs` — 코퍼스 오탐 회귀 섹션(양방향) + 기존 200여 체크 모두 통과.
- 65편 코퍼스 재실행: FP 계열 발화 0, 진짜 신호는 유지.
- README 「알려진 한계」에 보호 스팬·도메인 용어 한계 보충(같은 PR).
